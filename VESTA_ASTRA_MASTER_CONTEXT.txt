0. EXECUTIVE SUMMARY
====================

Vesta should not become "Cursor, but cheaper" and it should not spend years cloning the editor
surface, Tab completion or proprietary autocomplete training loop that Cursor already owns.

Vesta's strongest product category is:

    A LOCAL-FIRST, PROVIDER-NEUTRAL AI SOFTWARE ENGINEERING CONTROL PLANE
    THAT OPTIMIZES FOR VERIFIED ENGINEERING OUTCOMES PER UNIT OF COST/QUOTA.

The current market wedge is simpler and easier to explain:

    Vesta is the AI coding cost firewall.

Those statements are not contradictory. "Cost firewall" is the adoption wedge. The larger product
is the engineering control plane behind it.

The ideal Vesta workflow is:

1. A developer opens any existing repository in the editor/terminal they already use.
2. Vesta understands the repository locally before an expensive model starts wandering through it.
3. The developer asks for an engineering outcome, not a provider-specific prompt.
4. Vesta decides what deterministic/local evidence can solve first and what model/provider is
   actually required.
5. If work can be parallelized safely, Vesta decomposes it into bounded assignments, isolates them
   in worktrees, routes each assignment independently, and supervises them as an engineering team.
6. Commands, edits, Git/GitHub side effects, cloud spend and dangerous operations obey explicit
   authority and repository-safety rules.
7. Vesta does not treat a model saying "done" as proof. Required tests/checks/browser evidence and
   repository state determine the terminal verdict.
8. The user gets one truthful result and receipt: what happened, what changed, what was verified,
   what remains uncertain, which model/provider was used, and what it cost/saved.
9. The same task remains one task whether viewed from desktop, CLI, IDE bridge, background worker
   or future integration.

If Vesta reaches that experience while remaining easy to install and pleasant to use, it does not
need to beat Cursor at Cursor Tab to become a genuinely better product for a substantial class of
software engineers.

- Web UI assets are packaged inside the Python application.

The README's current first-order promise is accurate:

    Vesta is the AI coding cost firewall.

It sits in front of AI coding providers/clients and tries to route work through the cheapest safe
path that can genuinely complete the job. The intended order is approximately:

    deterministic tools
      -> compact cached/local context
      -> local/free capability
      -> confirmed cheap cloud capability
      -> stronger/expensive model only when evidence says it is justified

That is more than a pricing trick. It changes what the product controls. Vesta can observe the
engineering process around the model: repository state, edits, commands, tests, verification,
retries, Git/GitHub delivery and receipts. That makes it possible to optimize the total cost of a
successful result instead of the nominal price of one inference.

Existing user-facing concepts include:
- Desktop chat/control center.
- Model/provider selection including Auto, connected account CLIs, free-tier APIs and local
  endpoints where configured.
- Run modes: Ask, Plan, Safe Auto, Approve Edits, Full Auto.
- Visible activity/work log.
- Real cancellation with process-tree teardown as a product requirement.
- Inspector/settings surfaces.
- Money-saved / receipt concepts.
- Explicit GitHub push/PR consent.
- Repository identity and worktree safety.
- Verification policy and evidence execution.
- CLI routing, doctor, context, benchmarks, governance and receipts.
- MCP/tool/agent/workflow registries.
- Multi-agent/worktree primitives.
- Background-run/schedule primitives.
- Release/update/signing machinery.

Vesta is NOT a single giant agent. The Vesta Hub design is a registry/routing layer spanning tools,
agents, workflows, MCP servers and model tiers. OPcoding is the legacy-compatible lower-level
system that contains existing project scans, tests, GitOps and related foundations. New work should
prefer the current Vesta/vestahub architecture and treat opcoding compatibility carefully rather than
building a second product around it.


2. THE USER PROBLEM VESTA SHOULD OWN
===================================

Modern AI coding creates five connected problems:

A. MODEL/PROVIDER WASTE
Developers routinely use expensive frontier capability for work that deterministic tools, code
search, local models or cheaper models could solve. Provider subscriptions and API usage are
fragmented and opaque.

B. MODEL LOCK-IN
A great model this month may be mediocre next month. A product tightly coupled to one provider
forces the user to inherit that provider's economics, outages, rate limits and product decisions.

C. "DONE" IS TOO EASY TO SAY
Coding agents can generate plausible prose while tests fail, files did not change, changes happened
in the wrong checkout, a PR was never opened, or the requested behavior was not independently
verified. The product must distinguish a response from an engineering outcome.

D. AGENT SCALE CREATES SUPERVISION PROBLEMS
Once multiple agents operate in parallel, the hard problem becomes ownership, isolation,
reconciliation, budget, cancellation, verification and state continuity. More agents without a
control plane can make engineering less reliable.

E. POLISHED COMPETITORS HIDE SETUP COMPLEXITY
A technically better engine still loses if a developer has to clone a Python repo, install
special dependencies, understand internals and debug provider setup before the first useful task.
Distribution and first-run UX are product strategy, not packaging trivia.

Vesta should own the combined answer:

    "Give me the engineering outcome. Use the best available combination of tools/models at the
     lowest sensible total cost, keep it safe, prove it, and show me what happened."


3. THE NON-NEGOTIABLE PRODUCT INVARIANTS
========================================

Every meaningful feature should preserve these invariants.

3.1 ONE CANONICAL TASK/RUN TRUTH
One request should map to one task identity, ordered event history and evidence-backed state.
Desktop, CLI, background processes and integrations must not independently invent completion,
cancellation, cost or side-effect state.

3.2 PROVIDER NEUTRALITY
Claude, Codex/OpenAI, Copilot, Gemini, local models and future providers are capabilities, not the
product identity. Manual model selection must remain possible. Auto should route by outcome,
policy, cost and evidence rather than brand preference.

3.3 LOCAL-FIRST WHERE TECHNICALLY PRACTICAL
Repository understanding, policy, state, receipts and deterministic inspection should stay local
by default. Cloud/provider calls occur because the task needs them and policy allows them, not
because the architecture assumes a hosted Vesta brain.

3.4 DETERMINISTIC EVIDENCE BEFORE MODEL TOKENS
Use Git, parsing, tests, structured repository inspection, cache, symbol/index signals and bounded
local tooling before paying a model to rediscover deterministic facts.

3.5 EXPLICIT PAID/CLOUD AUTHORITY
Do not silently spend money or scarce subscription quota. Authority must be clear, bounded and
attributable to the current task/run/operation.

3.6 REPOSITORY SAFETY
Revalidate canonical repository/worktree identity before mutation. Branch movement, remote
changes, unknown scope, conflicts or unrelated user edits should block/serialize unsafe work
instead of guessing.

3.7 REAL CANCELLATION
"Cancelled" cannot mean "the UI stopped listening while a provider/command kept running." Owned
controllable work must be terminated/reconciled, and restart recovery must not duplicate work.

3.8 VERIFICATION-BACKED COMPLETION
Model prose is not system evidence. A model cannot promote its own claim to "verified". Required
checks, repository evidence, browser evidence and delivery evidence decide the result.

3.9 HONEST UNKNOWN / PARTIAL STATES
Unknown cost is not zero. Missing evidence is not pass. A timeout is not success. A model response
with no expected diff is not a completed edit. If Vesta cannot prove something, it should say so.

3.10 COMPLETE COST PROVENANCE
Routing economics must include failed attempts, retries, fallbacks, repair turns and verification,
not only the final successful model call.

3.11 CROSS-SURFACE PARITY
The same task viewed in desktop, CLI, IDE bridge or worker must not become multiple tasks or show
contradictory terminal state.

3.12 NO HIDDEN-CHAIN-OF-THOUGHT DEPENDENCY
Vesta needs structured reasons, facts and evidence—not private model reasoning. Route explanations
and receipts should be concise, inspectable and based on observable inputs.

5. CURRENT ARCHITECTURAL REALITY: STRONG PRIMITIVES, SOME DUAL TRUTH
===================================================================

A major strategic fact is that Vesta already has many of the hard primitives. This project should
not be rewritten from scratch.

The canonical-runtime epic (#818 at this snapshot) exists because durable state is not yet fully
consolidated. The repository contains a SQLite/journal direction plus legacy JSON/file/shadow
projections in several subsystems. This is visible in code, not just issue prose.

Example: vestahub/parallel_agents.py currently persists assignment JSON while recording a shadow
journal projection. It even documents a remaining concurrency issue: save itself is protected by
an interprocess transaction, but the broader check-then-claim flow can still race, so two claimants
may both pass an active-concurrency check. This is exactly the class of bug the canonical runtime
must eliminate rather than cover with another UI state.

Therefore:
- Do not add another durable state store because a feature needs convenience.
- Do not let GUI JavaScript become a second scheduler/router/verdict authority.
- Do not let background workers create their own task truth.
- Prefer moving subsystem authority behind the canonical journal incrementally.
- Preserve compatibility/migration only as long as required; legacy records should become inputs
  or projections, not peers with equal authority.


6. REPOSITORY SAFETY + MULTI-AGENT FOUNDATION ALREADY EXISTS
===========================================================

Vesta already has substantial parallel-agent machinery. In the current implementation:
- assignments have durable IDs/owners/status;
- intended-path overlap blocks unsafe parallelism;
- unknown scope is treated conservatively as potentially overlapping everything;
- assignments get isolated branches/worktrees;
- worktree leases and canonical repository handles are used;
- dirty paths are classified against intended scope;
- reconciliation refuses to silently merge changed-file collisions;
- workflow ledger evidence is recorded.

This means the multi-agent strategy is not "invent agents." The engineering job is to turn these
primitives into a first-class objective/assignment command center backed by canonical runtime,
verified outcome routing, bounded context and integrated verification.

Do not replace this safety model with a swarm framework that lets agents mutate one shared
checkout. More concurrency is not success. A benchmark must show improved objective-level
wall-clock or quality without unacceptable cost/conflict growth.


7. VERIFIED OUTCOME ROUTING IS THE CENTRAL MOAT
===============================================

The original cost firewall can be copied if it remains only:

    "try free/local, then cheap, then expensive"

The defensible version is issue #819's concept: the Verified Outcome Router.

The question is not:

    "Which model is cheapest?"

It is:

    "For this class of engineering work, this repository, this user policy and current provider
     health/quota, what route minimizes TOTAL expected cost while still achieving a verified
     outcome at the required quality/latency?"

Total route economics should include:
- first attempt cost;
- context/retrieval cost;
- latency;
- tool compatibility;
- test/verification cost;
- failure probability;
- repair/retry/fallback cost;
- quota scarcity;
- manual correction/revert signals;
- final verified/delivered outcome.

A €0.01 model that fails three times and forces a €0.50 rescue is not a €0.01 route.
A €0.08 model that finishes and verifies first pass may be the cheaper outcome.

Recommended user intents remain simple:
- Cost: minimize expected total verified cost subject to a success-confidence floor.
- Balanced: optimize verified outcome, latency and cost.
- Maximum: maximize verified success/quality while still avoiding obviously wasteful routes.

The learning path should be local-first:
1. Start with deterministic capability constraints and scorecards as priors.
2. Record privacy-safe outcome features—not private source/prompts merely for training convenience.
3. Learn local per-user/repo/task-class calibration.
4. Decay stale model/provider evidence.
5. Quarantine known-broken provider/model/version combinations quickly.
6. Explore alternatives only within bounded cost/risk policy.
7. Add optional privacy-preserving aggregate intelligence later if it earns its complexity.

North-star routing metric:

    VERIFIED ENGINEERING OUTCOMES PER EURO / UNIT OF SCARCE PLAN QUOTA

That is much harder for an editor-centric router to copy than simple per-turn price routing because
Vesta controls verification and delivery around the model call.


8. SEMANTIC CODE INTELLIGENCE: CLOSE A REAL CURSOR ADVANTAGE
============================================================

At this snapshot, semantic repository intelligence is strategically specified (#820) but should be
treated as an area requiring a live implementation audit before assuming it exists at product
quality.

The objective is not "add embeddings." The objective is:

    The expensive model begins with the smallest high-confidence slice of the repository needed
    to solve the task.

Desired local intelligence layers:
- file/directory/language/framework structure;
- definitions/symbols;
- imports/references/dependency relationships where practical;
- source <-> likely test relationships;
- config/build/entry points;
- changed/dirty/current revision signals;
- lexical search;
- structural neighbors;
- cached summaries;
- local/offline semantic representation;
- bounded snippet retrieval with provenance.

Retrieval hierarchy should remain cheap-first:

1. direct path/symbol match
2. lexical/code search
3. structural relationships
4. cached summaries
5. semantic retrieval
6. targeted file reads
7. provider-led exploration only when needed

Every context bundle should be able to say why a snippet was selected, what revision/worktree it
belongs to, how much context it consumes, and what relevant candidates were omitted. Measure
provider search/read calls and tokens avoided, not merely index speed.

Cursor has strong codebase indexing today, so this is not optional for long-term competitiveness.
But it does not need to block a first public alpha if release-critical reliability/distribution is
not ready. Ship the alpha honestly, then deepen the index behind a clean service boundary.


9. MULTI-AGENT COMMAND CENTER: THE PRODUCT BEYOND CHAT
======================================================

A long-term Vesta should feel less like "chat with a model" and more like supervising a small
engineering team.

One objective may contain:
- coordinator/planner;
- explorer/research assignments;
- implementation assignments;
- test/verification assignment;
- reviewer/critic assignment;
- integration/reconciliation assignment.

Each assignment should have:
- canonical identity;
- scope/intended files/symbols where predictable;
- dependencies;
- required capabilities;
- chosen route/provider/model;
- budget;
- isolated worktree/branch;
- activity state;
- changed files;
- verification target/evidence;
- terminal outcome and receipt.

The UI must answer at a glance:
- What is the overall objective?
- What has Vesta decomposed it into?
- Which parts are actually safe to run in parallel?
- Which agent/model owns each part?
- What is active, blocked, complete or failed?
- What changed?
- What did each assignment cost?
- What is ready for reconciliation?
- Did the integrated result verify?

The final objective is complete only after integrated verification. Child-agent consensus or
"looks good" prose is not verification.


10. ALWAYS-ON LOCAL WORKER
==========================

Cursor is moving engineering work into always-on cloud agents and automations. Vesta's structural
counter-position is a durable user-owned local worker, with optional self-hosting later, attached
to the same canonical runtime.

The worker should enable:
- scheduled tasks;
- bounded retry/maintenance;
- GitHub event-driven work;
- continuation after desktop closes;
- future webhook/integration triggers;
- reboot/restart reconciliation.

It must not inherit unlimited interactive Full Auto authority. Every unattended task needs an
explicit authority envelope: repository scope, operations allowed, cloud/paid permission, spend
cap, Git/GitHub permission, dangerous-action policy, expiry and notification behavior.

Duplicated events cannot create duplicated engineering work. Event identity and operation
idempotency matter more in an unattended system than in a chat window.


11. IDE STRATEGY: BE PRESENT, DO NOT BECOME AN IDE COMPANY
==========================================================

Cursor's biggest structural advantage is that it owns the editor loop, especially inline
completion and deeply integrated interaction. Vesta should not burn years rebuilding VS Code.

The high-leverage answer is thin VS Code and JetBrains bridges (#824):

    Editor supplies context and interaction.
    Vesta supplies intelligence, orchestration, policy, cost and truth.

Bridges should provide:
- Ask/Implement/Review/Explain Selection actions;
- active file/selection/diagnostics attachment with visible disclosure;
- task launch and control;
- status/blocked/approval/completion notifications;
- native diff/file/range opening;
- links into the full Vesta desktop Agents workspace;
- receipt/verification inspection.

The extension must NOT become another provider runtime or state authority. It should use one
versioned authenticated local protocol to the canonical Vesta runtime.

Explicit strategic non-goals:
- no VS Code fork;
- no Vesta editor;
- no giant bespoke autocomplete/Tab model program;
- no duplicated repository index inside every editor plugin.


12. BROWSER ENGINEERING MODE
============================

For frontend/UI work, source-only agents guess too much. Vesta's browser mode (#825) should convert
browser observations into structured verification evidence.

Use a mature boundary such as Playwright rather than inventing a browser driver.

Capabilities should include:
- isolated browser session;
- local/allowed URL policy;
- DOM and accessibility inspection;
- computed style/layout;
- console errors;
- failed/network requests with secret redaction;
- screenshots/regions;
- viewport presets;
- form/keyboard/mouse interaction;
- deterministic waits.

The product distinction should be evidence:
- screenshot is evidence, not automatic proof;
- console/network state is structured evidence;
- expected element/route/interaction checks can join verification policy;
- before/after screenshots attach to the canonical run/receipt;
- browser work obeys the same cancellation/authority rules as commands and Git operations.


13. CURRENT CURSOR COMPETITIVE BAR — 2026-09-06 SNAPSHOT
========================================================

This section comes from current official Cursor docs/blog material reviewed on 2026-09-06. Refresh
it before future strategy decisions.

Cursor currently competes with much more than an AI editor sidebar:

A. MULTI-MODEL + ROUTING
Cursor supports models across OpenAI, Anthropic, Google and others, plus its own Cursor models.
Cursor Router/Auto routes requests by task/complexity and exposes Cost, Balance and Intelligence
optimization modes. This means "we support many models" and "we auto-route by cost" are not, by
themselves, durable Vesta differentiation.

B. CLOUD AGENTS
Cursor Cloud Agents run in isolated cloud VMs with repositories, dependencies, secrets, network,
testing and browser/computer control. They can operate in parallel and across multiple repos.

C. MULTI-AGENT / WORKTREES
Cursor's Agents Window supports parallel agents/subagents, worktrees and multi-root workspaces.
Vesta cannot claim multi-agent leadership merely because it can spawn two processes. It must win on
provider neutrality, safe isolation, verified integrated outcomes and complete economics.

D. AUTOMATIONS
Cursor Automations run Cloud Agents on schedules and source-control/Slack/Linear/PagerDuty/webhook
triggers. Vesta's local worker must therefore be excellent, not just a cron wrapper.

E. SEMANTIC INDEXING
Cursor publicly describes semantic codebase indexing as a major agent-performance driver and has
invested heavily in large-repo onboarding. Vesta needs a credible local-first code intelligence
story.

F. BROWSER CONTROL
Cursor Agent can navigate, click/type, inspect screenshots, read console/network state and run
browser-based testing. Vesta Browser Engineering Mode needs to differentiate through canonical,
verification-backed evidence and safety—not just "we can open Chromium."

G. BUGBOT / CODE REVIEW
Cursor has a mature dedicated code-review product and has publicly reported improvements in speed,
cost and bugs found. Vesta should not add a generic "review agent" checkbox and call parity achieved.
A future Vesta review loop should combine code intelligence, repository history, verification,
provider routing and outcome feedback.

H. DISTRIBUTION/POLISH
Cursor's biggest practical advantage remains simple: normal developers can install it and get to
value quickly. Vesta loses before its moat is visible if setup is harder than the problem it solves.

14. HOW VESTA CAN ACTUALLY BEAT CURSOR
=====================================

"Destroy Cursor" should be interpreted as winning developer preference and engineering outcomes in
areas where Vesta has a structural right to win—not literally copying or harming a competitor.

The winnable battles are:

14.1 COST PER VERIFIED OUTCOME
Cursor has routing, but Vesta can own the entire outcome ledger: attempts, commands, tests, repair,
verification, delivery and receipts. Optimize what it costs to finish correctly, not one model
turn.

14.2 PROVIDER + ACCOUNT NEUTRALITY
Make the model market compete inside Vesta. Users should be able to exploit their existing account
CLIs, APIs, free tiers and local models instead of repurchasing intelligence through one vendor
where technically/legal-policy compatible.

14.3 LOCAL-FIRST PRIVACY + INSPECTABILITY
Repository understanding, state, receipts and learned calibration can remain local. Users can see
why Vesta routed, what it observed and what it proved.

14.4 TRUTHFULNESS / RECOVERABILITY
Make it difficult for Vesta to lie by architecture. One journal, idempotent side effects, explicit
unknowns, robust cancellation, worktree identity and verification-backed completion can become a
trust moat.

14.5 PROVIDER-NEUTRAL MULTI-AGENT ORCHESTRATION
An objective can use the best provider for each assignment instead of an ecosystem-owned model
fleet. Combine that with per-agent economics and safe worktree reconciliation.

14.6 EXISTING-TOOL CONTROL PLANE
Vesta can live beside VS Code, JetBrains, terminal and provider CLIs instead of demanding an editor
migration. Thin bridges are a feature of neutrality, not a compromise.

14.7 LOCAL UNATTENDED WORK
A user-owned worker can provide automation without requiring every engineering job to live in a
vendor cloud VM. Optional self-hosted/cloud paths may come later, but local-first should be real.

14.8 EVIDENCE AS A PRODUCT SURFACE
For code, browser/UI and delivery tasks, show proof. "What actually happened?" should be easier to
answer in Vesta than in any competitor.


15. WHAT VESTA SHOULD NOT TRY TO WIN RIGHT NOW
=============================================

Do NOT make these launch-blocking programs:

- Build a VS Code fork.
- Beat Cursor Tab/autocomplete quality head-on.
- Train a frontier coding model.
- Clone every Cursor setting or panel.

- Build a generic Zapier clone around automations.

A small team wins by choosing the right battlefield.

22. ENGINEERING WORKING METHOD FOR ASTRA/CODEX
=============================================

For every issue/bug/task, follow this sequence.

22.1 REFRESH REALITY
- Fetch current main HEAD.
- Read AGENTS.md.
- Read the target issue and recent related PRs/commits.
- Locate current implementation and tests.
- Check current Actions when release-sensitive.
- Treat this document's status section as historical if HEAD moved.

22.2 REPRODUCE BEFORE "FIXING"
For bugs, build the smallest real reproduction or failing regression test first where practical.
Do not patch from a screenshot description if code can prove the state transition that caused it.

22.3 FIND THE EXISTING AUTHORITY
Ask:
- Which module currently owns this fact?
- Is there already a canonical service/store?
- Is a UI layer recomputing backend truth?
- Is there a legacy/shadow path being migrated?
Prefer one authority over synchronization hacks.

22.4 MAKE THE SMALLEST COHERENT CHANGE
Small does not mean a one-line bandage. Fix the actual ownership/state boundary while avoiding a
cross-repo rewrite unrelated to the bug.

22.5 PROTECT INVARIANTS
Before writing, check implications for:
- run/task identity;
- repository/worktree safety;
- cancellation;
- paid/cloud authority;
- verification;
- cost provenance;
- update/recovery;
- cross-surface consistency.

22.6 TEST IN LAYERS
- focused unit/regression test;
- affected subsystem suite;
- relevant web/Playwright suite for UI behavior;
- required fast/CI profile where feasible;
- release profile for release-critical change.
Do not claim completion from a focused test if mandatory suites are red.

22.7 VERIFY THE BEHAVIOR, NOT JUST THE TEST
If the bug is visual, inspect the rendered UI. If it is update behavior, exercise the actual state
transition. If it is packaging, install the artifact. If it is cancellation, prove the owned process
is dead. Tests are evidence, but choose evidence that can observe the bug.

22.8 LEAVE A TRUTHFUL HANDOFF
Report:
- root cause;
- files changed;
- tests run and exact result;
- remaining known risk;
- whether current main/release checks are green;
- issue/PR linkage.
Never say "done" merely because code was written.

25. REPO-SPECIFIC TRAPS TO WATCH
================================

25.1 DUAL STATE / SHADOW JOURNAL
Some subsystems are migrating from JSON/files to journal projections. Fix authority, do not add
another mirror.

25.2 CLAIM-ASSIGNMENT CONCURRENCY
Current parallel-agent code documents a wider check-then-claim race not solved merely by atomic
save. Use multiprocess/idempotency thinking.

25.3 RUNNING VERSION != DISK VERSION
Updater work recently fixed confusion between code already replaced on disk and the still-running
old process. Never conflate "repository/artifact current" with "current process is running it."

25.4 SCHEDULER WAKE != REMOTE CHECK
A timer tick or cached result must not advance "checked remotely" truth. Manual update checks have a
stronger evidence obligation.

25.5 UPDATE OWNER MATTERS
Source checkout, native packaged app, pip/pipx/Homebrew/managed install can have different update
authorities. The wrong updater successfully mutating the wrong copy is worse than refusing.

25.6 UI TESTS CAN PIN THE WRONG THING
Past commits found tests asserting buggy states or tests incapable of observing the UI element they
claimed to validate. A passing test has value only if it can fail for the real regression.

25.7 MODEL PICKER / CONNECTION TRUTH
Provider connected state, available models and persisted verified CLI capability must have one
source of truth. Recent Codex fixes indicate this boundary deserves regression coverage.

25.8 OPCODING IS LEGACY-COMPATIBLE
Do not build new product identity around it because it exists. Preserve useful foundations while
moving new authority into Vesta/vestahub.

25.9 ARCHIVED STRATEGY DOCS EXIST
README references archived older commercial/business plans. Current free-public-alpha policy and
current strategic issues take precedence over archived hypotheses.

25.10 SOURCE DEV EXPERIENCE != PUBLIC INSTALL EXPERIENCE
A contributor command succeeding in a checkout does not prove a normal user can install/use the
artifact.

27. BENCHMARKS THAT MATTER
==========================

Benchmarks should model engineering outcomes, not synthetic model trivia.

ROUTING BENCHMARKS
- fix a known failing unit test;
- review a diff containing seeded logic/security/performance faults;
- bounded cross-file feature;
- documentation-only task;
- architecture/explanation task;
- provider failure requiring fallback.
Measure total cost to verified completion, first-pass completion, retries and latency.

CONTEXT BENCHMARKS
- locate bug source;
- find implementation behind API/controller;
- trace dependency/call path;
- identify likely tests;
- unfamiliar large-repo question;
- cross-file refactor.
Measure useful-context latency, tokens, redundant searches/reads and verified success.

MULTI-AGENT BENCHMARKS
Choose tasks with real independent work:
- multiple independent bugs;
- feature + tests + docs;
- separable module migration;
- simultaneous investigation branches;
- multiple GitHub issues.
Compare against one-agent execution on wall time, total cost, conflicts, verification and human
intervention. If multi-agent merely burns more tokens, do not ship it as default.

RELEASE BENCHMARKS
- clean install;
- first useful task time;
- upgrade;
- interrupted update;
- rollback;
- uninstall/reinstall;
- provider discovery;
- offline startup.

34. FINAL PRODUCT DOCTRINE
==========================

Vesta should be ambitious, but its ambition must be architectural rather than performative.

Do not win by showing more agent animations.
Do not win by listing more model logos.
Do not win by copying every Cursor panel.

Win by making the following statement true in production:

    Vesta takes an engineering objective, understands the repository efficiently, chooses the best
    available combination of tools and models, performs the work under explicit authority,
    isolates concurrent changes, verifies the integrated result, accounts for every attempt and
    leaves one truthful, recoverable record—all while remaining provider-neutral and local-first
    wherever practical.

The cost firewall is the wedge.
Verified outcome economics is the moat.
Canonical truth is the foundation.
Semantic code intelligence is the efficiency engine.
Multi-agent orchestration is the scale layer.
IDE/browser/worker surfaces make the control plane ubiquitous.
Simple installation is what allows any of the above to matter.

If a proposed change does not make Vesta safer, easier to adopt, more truthful, more capable at
verified outcomes, or materially more efficient, ask whether it should exist before spending the
release window on it.
