# Provider Permissions and Dispatch Performance Design

## Problem

OPai presents editable modes but does not carry that promise consistently to every provider surface.

1. `handle_gui_message` resolves an effective Full Auto preference and then replaces every Implement or Ship request with `safe-auto`.
2. The free API branch calls `app_state.ask(..., allow_edits=False)` unconditionally. Gemini, Groq, and Mistral therefore use the answer-only `run_ask` path, which has no repository tools.
3. Explicit free-model calls are routed through recommendation, result-cache, fingerprint, and evidence work intended for Auto mode. A mutating request must not reuse a cached prose answer, and the repeated work delays provider dispatch.
4. Project activation writes instructions for Codex, Claude, Copilot, Cursor, and Cline, but not Gemini CLI. OPai also has no Gemini CLI mode adapter, so an external Gemini session can remain in its own default or Plan approval mode regardless of the OPai mode.
5. Existing activated projects may retain an older managed instruction block until activation or repair refreshes it.

The result is a capability contradiction: the UI and prompt may authorize edits while the selected transport is physically answer-only or launched with read-only permissions.

## Goals

- Preserve the centralized Explain, Review, Implement, Ship, and Dangerous intent decision.
- Preserve a pinned Full Auto selection for authorized implementation turns.
- Give built-in Gemini, Groq, and Mistral API models bounded repository tools in editable modes.
- Keep Ask, Plan, Explain, Review, and Dangerous turns read-only regardless of provider.
- Add Gemini CLI project instructions and deterministic OPai-to-Gemini approval-mode mapping.
- Remove redundant explicit-provider routing and caching work from the send path.
- Make provider capability claims truthful and testable without live provider credentials.

## Non-goals

- No unrestricted shell for free API models.
- No write access outside the active repository.
- No automatic installation, authentication, or live invocation of Gemini CLI.
- No live paid or cloud calls in the test suite.
- No weakening of destructive-command, secret, production-credential, or force-push gates.

## Architecture

### Provider capability contract

Add a small immutable provider capability description in `opaihub/provider_adapters.py`. It states whether a provider supports repository reads, validated patch edits, test execution, native tools, streaming, and the concrete mode vocabulary it accepts. Mode resolution happens once before dispatch and returns a normalized execution plan.

The plan follows these rules:

- Explicit read-only intent always produces `ask` or `plan` and exposes no mutating tools.
- Implement and Ship use `safe-auto` unless the effective GUI mode is an acknowledged, pinned `full-auto`.
- A provider may receive only capabilities supported by both the user policy and provider contract.
- A capability mismatch is surfaced as a structured error; OPai never silently claims a write succeeded.

### Built-in API agent loop

Extend `FreeAPIRunner` with a bounded OpenAI-compatible tool-call loop. Editable runs expose only repository-scoped operations backed by `AgentComputerInterface`:

- list/find repository files;
- search repository text;
- read bounded file slices;
- validate and apply a unified patch;
- run an allowlisted project test command.

The loop is limited by iteration count, patch size, output size, cancellation, and timeout. Tool arguments are parsed as JSON and rejected on malformed input. `AgentComputerInterface` remains the enforcement boundary for repository containment and destructive-command rejection. Safe Auto permits validated edits but does not grant arbitrary commands. Full Auto removes repeated edit confirmations inside the active repository but still cannot force-push, delete user work, expose secrets, change production credentials, or escape the repository.

Read-only free-model turns retain the single-completion path and receive no mutating tool schema.

### External Gemini CLI integration

Project activation writes and refreshes `GEMINI.md` using the same managed-block renderer as the other clients. Global integration installs an `opai-gemini` wrapper when shell integrations are requested. The wrapper activates the current project, delegates capture through `opai agent-launch`, and falls back to the raw executable using the existing wrapper contract.

Gemini CLI arguments follow its current documented approval modes:

- Ask/Plan: `--approval-mode=plan`
- Safe Auto: `--approval-mode=auto_edit`
- Full Auto: `--approval-mode=yolo`

The mapping is generated by a pure function and covered with fake-executable tests. OPai does not persist YOLO as a Gemini default and does not bypass Gemini administrative policy.

References:

- <https://github.com/google-gemini/gemini-cli/blob/main/docs/reference/configuration.md>
- <https://github.com/google-gemini/gemini-cli/blob/main/docs/cli/cli-reference.md>

### Dispatch performance

Explicit provider selection bypasses Auto recommendation and answer-cache lookup. The GUI builds one repository/task packet and passes it to the provider path; the free-model path does not collect a second generic evidence snapshot. Mutating turns never read or write the prose result cache.

Verification uses deterministic call-count assertions plus a local benchmark with a fake transport. The required invariant is one bounded context snapshot and zero recommendation/cache calls for an explicit provider. The before/after benchmark records median time to the first provider invocation; the change must improve that path without a flaky wall-clock threshold in CI.

## Data flow

1. GUI resolves current preferences with `effective_mode`.
2. `resolve_agent_policy` classifies the latest explicit user request.
3. Provider adapter intersects policy capabilities, effective GUI mode, and provider capabilities into one execution plan.
4. OPai resolves and persists active repository context once.
5. OPai builds one redacted task packet.
6. Account CLI providers receive their native permission flags.
7. Free API providers receive either a read-only completion or a bounded repository-tool loop.
8. The result reports effective mode, tools invoked, changed files, tests, and any capability blocker truthfully.

## Error handling and safety

- Malformed tool calls return a structured observation to the model and consume one bounded iteration.
- Paths outside the repository fail closed.
- Patch validation runs before patch application.
- Conflicting dirty paths block the affected edit; unrelated dirty paths are preserved.
- Cancellation interrupts both HTTP transport and the agent loop.
- Timeouts and iteration exhaustion return partial, structured results without claiming completion.
- Provider credentials never enter prompts, logs, receipts, or test fixtures.
- Cloud confirmation remains mandatory before a free API request leaves the device.

## Testing

### Unit tests

- Mode resolution preserves pinned Full Auto and downgrades unpinned Full Auto.
- Explain/Review/Dangerous remain read-only in every provider.
- Gemini CLI mode arguments map exactly to Plan, Auto Edit, and YOLO.
- Provider capabilities intersect with policy capabilities.
- Tool-call JSON, iteration limits, patch limits, paths, cancellation, and timeouts fail safely.
- Explicit provider dispatch bypasses recommendation and result cache.

### Integration tests

- Project activation creates and idempotently refreshes `GEMINI.md` without overwriting user text.
- Shell wrappers include Gemini and preserve passthrough behavior.
- A fake free API model reads a file, returns a patch tool call, applies it inside a temporary Git repository, runs a focused test, and returns changed-file evidence.
- The same fake model cannot edit in Ask, Plan, Explain, Review, or Dangerous modes.
- Account providers receive the preserved effective mode.

### End-to-end and regression tests

- Web/desktop pipeline tests cover Gemini API Safe Auto and pinned Full Auto turns through the real dispatch pipeline with a fake transport.
- Existing Claude, Codex, Copilot, local-model, cancellation, autonomy, security, and activation suites remain green.
- Full Python, pytest, JavaScript unit, and browser E2E suites run before the PR is marked ready.
- Ruff, Bandit, dependency audit, secret scan, installer validation, and clean-wheel smoke remain release gates.

## Rollout

The change is backward-compatible for read-only turns. Activated projects gain `GEMINI.md` on the next activation or repair. Built-in free models use tools only when the centralized policy authorizes edits and the user has already crossed the existing cloud-confirmation boundary.
