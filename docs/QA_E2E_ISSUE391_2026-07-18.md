# Issue #391: Error, Empty, Loading, and Degraded State Audit

## State map

| View | Loading | Empty | Error / degraded | Safe action | Verified by |
| --- | --- | --- | --- | --- | --- |
| Workspace chat | Canonical prepare, context, model, connect, and send activity phases | Composer explains the fastest way to start | Rich terminal error card has a reason, `role="alert"`, explicit recovery buttons, and opt-in redacted details | Retry, edit prompt, settings, reconnect; never automatic | `state-framework.spec.js`, `errors-recovery.spec.js` |
| Dashboards | "Loading dashboard" while the local bridge prepares data | Short reason plus "Open chat" | Malformed payload and bridge errors are alerts; offline/degraded is a polite status and preserves chat | Manual "Try again" for failures; "Open chat" for empty/degraded | `state-framework.spec.js`, `async-data.spec.js`, `loading-states.spec.js` |
| Settings | "Loading settings" / "Checking local preferences and connections." | Settings renders its explicit zero-data controls | Malformed payload and bridge errors are alerts; a degraded local response is a polite status | Manual "Try again" only | `state-framework.spec.js`, `async-data.spec.js`, `loading-states.spec.js` |
| Sidebar recents | Boot data is local and immediate | "No saved chats yet" plus "New chat" | No remote request or automatic recovery | New chat | `state-framework.spec.js`, `folder.spec.js` |
| Global notifications | No fake progress | N/A | Toasts are a polite, atomic status region | Explicit control remains with the user | `state-framework.spec.js`, `accessibility.spec.js` |

## Accessibility and safety checks

- Error cards announce once through `role="alert"`; status cards use polite live
  regions to avoid interrupting active work.
- Technical parser details, prompts, credentials, and stack traces are not put
  into state-card copy. Chat error details remain opt-in and redacted.
- All recovery actions are clicks. No state card triggers a new model call,
  provider reconnect, or paid operation by itself.
- Loading wording describes real bridge or workspace phases and does not imply
  percentage completion.

## Acceptance scenarios

- Provider unavailable / expired / rate limited: existing typed chat errors
  retain the reason and appropriate recovery action.
- Empty ledger / empty recents: a useful explanation and the shortest next
  action are present.
- Slow dashboard / settings data: semantic loading state remains until the
  worker response replaces it.
- Offline/degraded dashboard: data freshness is explained, an alert is not
  spammed, and the user can continue to chat without an automatic retry.
